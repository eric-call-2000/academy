# Web Security Basics — think like an attacker, ship like a defender (id: `sec`, icon 🛡️, Intermediate, 7h, 33 items, sits between Course 7 and Course 8)

## Verdict
STANDALONE — but only because folding it fails on arithmetic, not on principle. The owner's instinct ("some of this can live inside the auth unit of Course 7") is right about exactly 4 items: password hashing, 401-vs-403 roles, login rate limiting, and not leaking stack traces. Those genuinely belong next to `srv-u5`. The other ~29 items have no home there: Course 7 is server-only, and more than half of this material is client-side (XSS, DOM sinks, escaping, sanitizing, CSP, secrets in shipped source, token storage). Course 7 is already 38 items / 8h; absorbing 29 more puts it at 67 items — 34% past the largest course in the catalog (Learn JavaScript, 50). It stops being a course and becomes a boxed set.

The second reason is pedagogical and it's the stronger one: security is the only proposed course where the existing sandbox is not a compromise but an *advantage*. The `web` runtime is a real sandboxed iframe with `allow-scripts` — an `<img src=x onerror=...>` payload injected via `innerHTML` genuinely executes, and the grader script runs in the same document, so it can read a sentinel the payload set. The learner writes a working exploit, watches it fire, then closes the hole and watches the same assertion flip. No other proposed course (shell, git, npm, deploy) gets that for free. Splitting that experience across two courses wastes it.

So: standalone, and DON'T split. Keep hashing here, because a course that teaches login rate limiting and vague error envelopes but hands password storage to a different course can't teach "the login endpoint, end to end" — which is the single most valuable hour in the whole thing.

Two placement calls that follow from this:
1. Catalog position 8, BEFORE Full-Stack Capstone. The capstone builds his portfolio app; he should build it already knowing not to `innerHTML` a note title. Course 8's `cap-u5` ("Polish & a11y") should later grow 2-3 hardening steps and be retitled "Polish, a11y & hardening" — that's a separate small edit, not part of these 33 items.
2. One surgical edit to Course 7 today: `srv-u5`'s quiz explanation currently ends "the day you add roles — 'only admins may delete' — that valid-but-forbidden case becomes your first 403." That's a dangling promise. Point it at `sec-u6-1` instead.

What this course is NOT: cybersecurity. No ports, no nmap, no threat-model workshops, no TLS handshakes, no `npm audit`. It is application security for one person shipping one web app. Supply-chain belongs in the proposed Node/npm course; HTTPS/domains belong in the proposed Deploy course. Holding that line is what keeps it at 33 items.

## Engine needs
Three additions, in descending order of necessity. Total honest estimate: ~300 lines of plain JS, no build step, no WASM, no CDN. NO shell, NO git, NO real SQL engine, NO Node process is required anywhere in this course — that is the main reason I'd build this one before the others on his list.

1. CSP NESTED-FRAME LAB — ~180 lines, the only genuinely new runtime. REQUIRED BY: `sec-u7-2` only.
Why it's needed: the preview iframe's `sandbox` attribute is fixed by `runWeb()`, and a learner-authored `<meta http-equiv=\"Content-Security-Policy\">` in `index.html` would apply to the rest of the document — including the grader script that `buildSrcdoc` injects before `</body>`. A policy strict enough to be worth writing kills the grader. Enforcement therefore has to happen one level down.
How to build it: a `harnessCspLab()` function alongside the existing `harnessCommon`/`harnessMock` in runner.js, stringified and injected only when `lesson.cspLab` is set (same gating pattern as `lesson.mock`, ~4 lines of change in `buildSrcdoc`). It exposes `window.__runCspLab(policyString)`, which creates a nested `<iframe sandbox=\"allow-scripts\" srcdoc=…>` whose head is: the learner's policy as a meta tag, then a fixed battery — an inline `<script>`, an `<img src=x onerror>`, an `eval()` call, an inline style, and an external-looking stylesheet built from a data: URI. Each payload writes into a local results object; a small reporter at the end of the child's body posts the object to `parent` via `postMessage`. The preview document listens, stashes it on `window.__CSP_RESULTS`, and the grader reads it after `await T.sleep(400)`.
Risk to spike BEFORE committing: nested sandboxed `srcdoc` frames inherit an opaque origin from an already-opaque parent, and I have not verified in Chrome that a `<meta http-equiv>` CSP is honored in that position. Budget half a day to prove it. If it fails, the fallback is honest and costs nothing: cut this lesson, ship U7 as four items, and teach CSP purely through the `parsePolicy`/`allows` interpreter in `sec-u7-1` while stating plainly in the brief that the browser is the thing that enforces it and this exercise is the semantics only.

2. `crypto-lite.js` — ~120 lines, a plain `<script>` next to `core.js`. REQUIRED BY: `sec-u6-3` (nice-to-have, not blocking).
Provides `sha256(str)` (pure JS, synchronous, the standard ~70-line implementation), `randHex(n)` (`crypto.getRandomValues` with a `Math.random` fallback), and `slowHash(str, salt, rounds)` (iterated sha256). It must reach the WORKER, which today only receives `harnessCommon` and `harnessMock` — so it also needs a `harnessCrypto()` in runner.js, stringified and concatenated in `buildWorkerSrc` and `buildSrcdoc`. One line each.
Why not `crypto.subtle`: it exists in workers and would give real PBKDF2, but it's async (awkward inside `T.eq`-style steps) and requires a secure context. `runJS` already has a `file://` fallback path, and `file://` is not secure, so `crypto.subtle` would be `undefined` for anyone opening `index.html` directly. Pure JS works everywhere.
Why it's NOT blocking: the same trick U4 uses for SQL works here — ship a 40-line hash prop inside `sec-u6-3`'s own `files` as read-only starter code, clearly labelled \"a toy, never ship this.\" The lesson then teaches salting, per-user salts and round counts (which is the actual learning objective) with zero engine change. `crypto-lite.js` is the v2 upgrade that makes the primitive real.

3. PROGRAMMABLE MOCKS (`lesson.mockFn`) — ~15 lines in runner.js. OPTIONAL, but the best value-per-line in the list and it pays off across Courses 6, 7 and 8 too.
Today `lesson.mock` is `JSON.stringify`'d into `harnessMock`, so it can only hold data. That means no test anywhere in the app can assert what the learner's `fetch` actually SENT — headers, method, body. For a security course that's a real ceiling: \"did you send the token?\", \"did you send the CSRF header?\", \"did you stop sending the API key?\" are all ungradeable through the mock.
Fix: accept `lesson.mockFn` as a JS SOURCE STRING (same convention as `step.test`, which is already a source string run in the sandbox). `harnessMock` evals it to get `(url, opts) => ({status, body})`, and pushes every `{url, method, headers, body}` onto `window.__CALLS` before answering. Tests then assert against `__CALLS`. Backwards compatible — `lesson.mock` keeps working untouched.

EXPLICITLY NOT NEEDED, and worth saying out loud because these are the expensive ones on his list: no simulated shell, no simulated git, no SQL engine. The toy SQL in `sec-u4-3` is ~60 lines of regex living in that ONE lesson's `files` array as starter code the learner reads but doesn't edit — precisely how `srv-u1-3` ships its `PETS` const. It handles two query shapes and one injection pattern. It is a teaching prop, not infrastructure, and it must never be promoted into the engine.

## Overlaps
Six real collisions in the existing 304. Five are near-misses that need a deliberate boundary; one is a direct hit.

1. DIRECT HIT — `dom-u1-3` "textContent vs innerHTML" (Course 5, Building Interactive Websites). This is already an XSS lesson. It has the `<img src=nope onerror=stealPasswords()>` payload, a step that grades rendering it safely, a cheatsheet note reading "NEVER innerHTML untrusted input — that's an XSS attack," and a quiz question whose correct answer is "Untrusted input parsed as HTML can inject scripts (XSS)."
AVOIDANCE: U2 must not contain a single step that grades "use textContent instead." That rule is taught, and re-teaching it is the fastest way to make this course feel like filler. Instead U2 inverts it — the learner writes the exploit and watches it fire, which `dom-u1-3` never does (there the payload is inert from the first line). The U2-1 brief should open by naming the earlier lesson explicitly: "In Learn Interactive Websites you were told not to do this. Now do it." And the U2 quiz must not reuse the "why is `msgEl.innerHTML = userComment` dangerous" question — it's already `dom-quiz-1`'s. U2's quiz covers stored-vs-reflected-vs-DOM, why `<script>` doesn't fire from innerHTML, and which sinks besides innerHTML are dangerous — none of which exist anywhere today.

2. `srv-u6-1` "Validate the body" — server-side `validateSignup` with required/min-length/contains-@ rules, returning an array of problem strings.
AVOIDANCE: U4 contains zero required-field validation. Its three ideas are orthogonal: allow-list vs deny-list (a *strategy* choice, not a rule list), canonicalization ORDER (decode before you check), and structure-vs-string (parameterized queries, argv arrays, refusing object-valued input). U4-1's brief should say "You already know how to check that a field is present — `srv-u6-1`. This is about checking it's *safe*, which is a different question with a different answer."

3. `srv-u5` "Auth-lite" (entire unit) — login, tokens, `activeTokens`, the 401 envelope, vague "invalid credentials," logout as revocation, and per-user list filtering in `srv-u5-3`.
AVOIDANCE: U6 issues no tokens and writes no login route from scratch — it inherits `token-ada`/`token-bo` as a given, exactly as `srv-u5-2` does. Its four ideas are all absent from Course 7: roles and a 403 envelope; IDOR on a single object with a 404 response; password hashing; rate limiting. The closest call is `srv-u5-3` (per-user filtering) vs `sec-u6-2` (IDOR) — the boundary is that `srv-u5-3` filters a LIST by the token's identity, while `sec-u6-2` fetches ONE object by an id the attacker chose, and its graded insight is that the miss must return 404 with a body byte-identical to the not-found case. Different bug class, different response code, different assertion.
BONUS: `srv-u5`'s quiz already contains the two setup lines for this course — the 401-vs-403 explanation ending "the day you add roles… becomes your first 403," and the plain-text-passwords explanation ending "real servers store slow-to-reverse HASHES (bcrypt and friends)." Both are promissory notes with nothing behind them today. `sec-u6-1` and `sec-u6-3` are literally the payoff. Edit those two `explain` strings to point at this course.

4. `srv-u6-3` "Never crash" — `safeHandler(handler)` wrapping throws into a 500 envelope.
AVOIDANCE: U1-3 "fail closed" is about what the ANSWER is when state is missing (deny), not about not crashing — and it's a permission function, not a request handler. The overlap is closed further by `sec-u6-4`, which adds the one thing `srv-u6-3` omits: the 500 body must leak nothing. Its test throws an error whose message contains a fake secret and a file path, then asserts the response body contains no `\"at \"`, no `.js`, and none of the message text. That's a new assertion on an existing wrapper, which is the right kind of overlap — it deepens rather than repeats.

5. `html-u4-6` "Built-in validation" (Learn HTML) — `required`, `type`, `pattern` on form inputs.
AVOIDANCE: rather than avoid it, use it. `sec-u1-2` "The client is not your friend" should open by naming it: "you wrote `pattern` and `required` in Learn HTML — here's the request that never opened your form." The client/server validation split is a genuine teaching moment and it currently exists nowhere.

6. `cap-u1-1` (localStorage API) and `cap-u4` (import/export). `sec-u5-3` uses localStorage but assumes the API is known and spends its steps on token theft. No teaching overlap. Similarly, `async-u6` optimistic UI and `dom-u5`/`dom-u6` (components, render loops) share only the render pattern that `sec-u3`'s project rebuilds — safely, which is the point.

NOTHING IN THE COURSE DUPLICATES: escaping (no `escapeHtml` exists anywhere in 304 items), sanitizing, allow-lists, canonicalization, injection of any kind, secrets/env vars/redaction, password hashing, roles/403, IDOR, rate limiting, CSP, or any security header. Grep confirms `403`, `hash`, `bcrypt` and `role` appear only inside quiz explanation prose in `srv-u5`, never as a graded step. The genuinely new surface here is ~28 of the 33 items.

## Units

### 1. Unit 1 — Trust boundaries: every input is a lie
Where data comes from decides how you treat it. Trusted vs untrusted sources (including the two that fool everyone: localStorage and your own API's responses), never trusting a client-supplied value that has money or permission attached, and failing closed when state is missing or malformed. This is the mindset unit; everything after it is a technique.

Lessons:
  - Every input is a lie
  - The client is not your friend
  - Fail closed
  - Unit 1 quiz: Trust & threat model

Graded how:
All three lessons are `js` (Web Worker), pure functions — the exact Course 7 pattern. (1) Learner writes `classify(source)` returning "trusted" or "untrusted" for nine named sources. Test asserts the full mapping, and specifically that `"localStorage"` → untrusted (the user edits it in devtools) and `"our own API response"` → untrusted (the DB may already hold a poisoned row). Two deliberate traps, both asserted by exact string equality. (2) Learner is handed a working `handleRequest` whose checkout route computes the total from `req.body.price`. Test first proves the hole: `POST /api/orders {id:"mug", price:0}` currently returns `total: 0`. Learner rewrites it to look the price up from a server-side `PRODUCTS` table and ignore the client's number; test re-posts the same forged body and asserts `total === 12`, asserts a legit order still works, and asserts an unknown id returns 400 rather than `NaN`. (3) Learner writes `canAccess(user, doc)`. Test throws eleven malformed shapes at it — `undefined`, `null`, `{}`, `{role:undefined}`, `{role:"ADMIN"}` (wrong case), a string, a number — and asserts every one returns exactly `false` with zero throws, while the one valid shape returns `true`. Deny-by-default is graded as "no input crashes it and no unexpected input passes."

### 2. Unit 2 — XSS: the attack lab
Reflected, stored and DOM-based XSS, by writing the exploits. Which sinks are dangerous (`innerHTML`, `outerHTML`, `insertAdjacentHTML`, `href`, `src`, `srcdoc`, `eval`), why `<script>` inserted via innerHTML does NOT run but `<img onerror>` does, and why that fact traps beginners into thinking they're safe.

Lessons:
  - Reflected XSS: pop your own payload
  - Stored XSS: one comment, every visitor
  - DOM XSS: know your sinks
  - The <script> tag that didn't fire
  - Unit 2 quiz: How XSS actually works

Graded how:
All four are `web` (real iframe). Mechanism: payload strings in the starter carry `onerror="window.__fired=(window.__fired||0)+1"`. The grader script runs in the same document, so it reads `window.__fired` directly. Every assertion is `await T.sleep(120)` first, because `onerror` fires async. (1) Search page renders `results.innerHTML = "You searched for: " + query`. The learner writes the payload into `const query` (labelled as the `?q=` value, since there's no URL bar). Test asserts `T.count('#results img') === 1` AND `window.__fired === 1` — the learner must actually land a working exploit to pass. (2) Comments board: test drives `T.type('#comment', PAYLOAD)` + `T.submit('#form')`, then calls the learner's `renderAll()` a second time and asserts `window.__fired >= 2` — proving persistence, which is the whole difference from reflected. (3) Learner converts three sinks in `render()`. Test asserts `T.text('#out')` contains the literal characters `<img`, `T.count('#out img') === 0`, and `window.__fired === undefined`. Fourth step is the scheme check: user-supplied `href` starting `javascript:` must be dropped — test does `T.click('#profileLink')` and asserts no fire, then asserts a legit `https://` avatar link kept its href (so the learner can't pass by nuking all links). (4) Learner assigns `out.innerHTML = '<script>window.__fired=1<\/script>'`; test asserts `T.count('#out script') === 1` (the element exists) and `window.__fired === undefined` (it never ran). Step two: same slot, `<img onerror>` payload → `__fired === 1`. Surprising, memorable, and both halves are hard assertions.

### 3. Unit 3 — Escaping, sanitizing and safe rendering
The three defenses, in order of preference: don't build HTML from strings at all (textContent / createElement / setAttribute); if you must, escape for the right context; if you must accept markup, allow-list it. Includes the double-escape ordering bug and why HTML-escaping is not enough inside an attribute.

Lessons:
  - Write escapeHtml
  - Escaping is context-dependent
  - An allow-list sanitizer
  - Project: The safe comment renderer
  - Unit 3 quiz: Escaping & sanitizing

Graded how:
(1) `js`. Learner writes `escapeHtml(str)` for `& < > " '`. Tests assert exact output on the unit's payload, assert `escapeHtml("&lt;")` === `"&amp;lt;"` (catches replacing `<` before `&` — the classic ordering bug, and the naive solution fails this), and assert `escapeHtml(null)` and `escapeHtml(42)` return strings instead of throwing. (2) `js`. Learner writes `escapeAttr` and `escapeJsString` plus a `pick(context)` dispatcher. The graded insight: given the input `x onmouseover=alert(1)`, the test asserts `escapeHtml` leaves it byte-identical (it contains no `<>&"'`) while `escapeAttr` neutralises it — proving HTML escaping is context-blind. Exact string equality on six cases. (3) `web` (needs the DOM — Workers have no DOMParser). Learner writes `sanitize(dirty)` that parses into a detached `<template>`, walks the tree, drops any tag outside `[B,I,EM,STRONG,A,P,BR,CODE]`, and strips every attribute except `href` on `A` where the scheme is http/https. Tests: `<b>hi</b>` survives with the `<b>` intact; `<img src=x onerror=...>` is gone and `window.__fired === undefined`; `<b onclick=...>x</b>` keeps the `<b>` element but `T.$('#out b').hasAttribute('onclick')` is false; `<a href="javascript:...">` keeps the anchor and loses the href; a nested `<p><b><img onerror></b></p>` payload is cleaned at depth. (4) PROJECT, `web`, 50xp/35min. Build a comment widget that renders `*bold*`/`_italic_`/bare URLs as real formatting while staying inert against four payloads. Graded in five step-groups: legit formatting produces real `<strong>`/`<em>` elements; all four payloads render as literal visible text with `window.__fired === undefined`; auto-linked URLs get `rel="noopener noreferrer"` and `target="_blank"` (asserted via `T.attr`); a `javascript:` URL in the text is NOT auto-linked; and `render.toString().indexOf('innerHTML') === -1` — grading the technique, not just the outcome (precedent: `dom-u7-3` already greps `startAnimation.toString()`). Every brief in this unit ends with the same honest line, and the quiz tests it: a hand-rolled sanitizer is a teaching exercise, ship DOMPurify.

### 4. Unit 4 — Validation and injection
Allow-lists beat deny-lists; canonicalize BEFORE you validate; and injection — SQL, NoSQL operator, command — is one bug wearing three hats: a string concatenated where a structure belonged. Deliberately does not re-teach required-field validation, which `srv-u6-1` already owns.

Lessons:
  - Allow-list, never deny-list
  - Canonicalize before you validate
  - Injection is a string-concatenation bug
  - Same bug, different language
  - Unit 4 quiz: Validation & injection

Graded how:
All four are `js`, pure functions. (1) Starter ships a working `badFilter()` deny-list that strips `<script>`. Step one asserts `badFilter("<img/src=x onerror=1>") === "<img/src=x onerror=1>"` — the learner watches the deny-list wave the payload through before writing anything. Learner then writes `isSafeUsername(s)` with a positive regex; tests assert it accepts `ada_99`, rejects the payload, rejects `ada 99`, rejects a 200-char string, rejects `""`, and returns `false` (not a throw) for `null`, `42` and `{}`. (2) Path traversal as a pure function. Starter ships a naive `checkNaive(name)` that rejects literal `..`; step one asserts `checkNaive("%2e%2e%2fetc%2fpasswd")` returns "allowed" — the bypass, proven. Learner writes `resolveUpload(name)` that `decodeURIComponent`s FIRST, then rejects `..`, `/`, `\\`, leading `.`, and a NUL byte. Tests assert both the raw and the percent-encoded payload are refused, that `report.pdf` is accepted, and that a double-encoded `%252e%252e` is also refused (decode-once is not enough — this step is what teaches order-of-operations). (3) The lesson's `files` include a ~60-line toy `runQuery(sqlString)` the learner does NOT edit — read-only starter code, exactly like the `PETS` const in `srv-u1-3`. It understands `SELECT * FROM users WHERE name = '…'`, `OR '1'='1'` and `--`. Step one: assert the vulnerable `findUser("' OR '1'='1")` returns all four users. Learner rewrites it to call the also-provided `runQueryParams(sql, params)`; test asserts the same payload now returns `[]`, that `findUser("ada")` still returns exactly one row, and that `findUser.toString().indexOf("'") === -1` in the query string — no quotes means no concatenation. NOTE: this is 60 lines of regex in a lesson file, NOT a SQL engine in the runner. (4) NoSQL operator injection. Learner writes `buildFilter(input)` that refuses object-valued input. Test passes `{"$gt": ""}` and asserts login is refused, passes `"ada"` and asserts it's accepted, passes `["ada"]` and asserts refusal. Second half: `safeArgs(cmd, userInput)` returns an argv ARRAY rather than a shell string; test asserts `safeArgs("convert", "a.png; rm -rf /")` yields exactly `["convert", "a.png; rm -rf /"]` — one argument, semicolon inert — and that the naive version produces a two-command string.

### 5. Unit 5 — Secrets, keys and where tokens live
There are no secrets in the browser: anything shipped to the client is public. What an env var is for, what must never be committed, and the real trade-off between localStorage and an httpOnly cookie for session tokens — demonstrated by stealing the token.

Lessons:
  - There are no secrets in the browser
  - Env vars, redaction and what never gets committed
  - Where a token lives: localStorage vs a cookie
  - Unit 5 quiz: Secrets & storage

Graded how:
(1) `web`, using the existing per-lesson `mock` fetch. Starter page has `const API_KEY = "sk_live_51H8x…"` used in a weather call. Step one: learner writes `findSecrets(text)` scanning for `sk_live_`, `AKIA`, `-----BEGIN` and a 32+ hex run; test runs it over the page's own `document.scripts[i].textContent` and asserts it returns a non-empty array — the learner proves the key is public by finding it in the shipped source. Step two: learner refactors the call to hit `/api/weather` (their own server, key-free, mocked); test asserts `findSecrets(allScriptText)` now returns `[]` AND that the weather still renders (so deleting the feature doesn't pass). (2) `js`. No filesystem, so: learner writes `loadConfig(env)` reading a plain `env` object and throwing an error whose message names the specific missing key (test asserts `/DB_PASSWORD/.test(err.message)`), `redact(config)` returning a loggable copy where `DB_PASSWORD`/`API_KEY`/`SESSION_SECRET` are `"***"` (test asserts the non-secret keys survive with real values and that `JSON.stringify(redacted)` contains none of the three secret values), and `shouldCommit(filename)` classifying `.env`→false, `.env.example`→true, `config.js`→true, `id_rsa`→false, `secrets.json`→false. Stated honestly in the brief: we cannot run git, so this grades the rule, not a real `.gitignore`. (3) `web`; localStorage is already shimmed by `harnessCommon`, so this works unchanged. Learner writes `saveSession(token)`/`readSession()`. Step two runs the page's pre-planted XSS payload, which does `window.__exfil = localStorage.getItem('token')` — test asserts `window.__exfil` equals the token, i.e. the theft succeeded. Learner then moves the token into a closure plus the starter's fake `cookieJar` marked `httpOnly:true`; test asserts `window.__exfil` stays `null` after re-running the same payload, that `readSession()` from outside the closure returns `null`, and that `authFetch()` still reaches the mocked endpoint. Labelled a simulation in the brief — the sandbox has no real cookie jar, and the lesson says so rather than pretending.

### 6. Unit 6 — Authorization, passwords and abuse
Authentication is who you are; authorization is what you may do — and Course 7 only taught the first. 401 vs 403, roles, IDOR on a single object (and why 404 beats 403 there), never storing a password, and rate limiting the login. Reuses Course 7's exact ada/bo/token-ada world so it reads as srv Unit 9.

Lessons:
  - 401 vs 403: roles
  - IDOR: an id in the URL is a request, not a permission
  - Never store a password
  - Rate limits, lockouts and identical failures
  - Unit 6 quiz: Authz & credentials

Graded how:
All four `js`, extending `handleRequest`. (1) Users gain a `role`. Learner writes `requireRole(req, role)` and guards `DELETE /api/posts/1`. Tests assert four outcomes: no token → 401 `{error:"unauthorized"}`; valid non-admin token → 403 `{error:"forbidden"}` (a different envelope from 401 — asserted by deep equality); admin token → 204 AND the post is actually gone from the store; and that a non-admin's failed DELETE left the store untouched (length unchanged) — the guard must run before the mutation, not after. (2) `GET /api/notes/:id` where each note has `ownerName`. Tests: ada's token on ada's note → 200 with the note; ada's token on bo's note → exactly 404, NOT 403, and the body must be byte-identical to the body returned for a note id that doesn't exist at all (`T.eq(JSON.stringify(a), JSON.stringify(b))`) — that identity is the graded insight, because a 403 confirms the row exists. Distinct from `srv-u5-3`, which filters a list; this is a direct-object fetch. (3) Learner writes `makeUser(name, password)` generating a random salt, `hashPassword(password, salt, rounds)` on top of a provided slow-hash primitive, and `checkPassword(user, attempt)`. Tests: `JSON.stringify(user)` contains neither the plaintext nor any 4-char substring of it; two users created with the SAME password have different `.hash` (proves the salt is per-user, and a global-salt solution fails here); `checkPassword` true for the right password and false for the right password with one character changed; the record carries `salt` and `rounds`; and `rounds >= 10000`. (4) Learner writes `rateLimit(store, key, max, windowMs)` and wires it into login. Tests: five wrong passwords each return 401, the sixth returns 429 with a `Retry-After` in the body, and — the point — the CORRECT password on the seventh attempt also returns 429, because the limit keys on the identity, not the outcome. Second half asserts the 401 body for "unknown user" and "wrong password" are byte-identical via `T.eq(JSON.stringify(a), JSON.stringify(b))`, and that a thrown internal error produces a 500 whose body contains no `"at "`, no `.js`, and none of the error's own message text (stack-trace leakage — which `srv-u6-3` does not cover).

### 7. Unit 7 — Browser defenses and the hardening capstone
The headers a shipped app sets and why: Content-Security-Policy as a second line of defense after escaping, X-Frame-Options/frame-ancestors against clickjacking, nosniff, Referrer-Policy, HSTS. Then the whole course applied at once to a deliberately broken app.

Lessons:
  - CSP: read the policy
  - CSP for real: the nested-frame lab
  - Security headers & clickjacking
  - Project: Harden ShoutBoard
  - Final quiz: Web Security Basics

Graded how:
(1) `js`, works today. Learner writes `parsePolicy(str)` → object and `allows(policy, directive, url)` implementing `'self'`, `'none'`, exact hosts, wildcard subdomains, and the fallback to `default-src` when a directive is absent. Tests assert exact booleans on ten cases, including the two that matter: `img-src` unspecified falls back to `default-src`, and `'unsafe-inline'` present means an inline handler is allowed. Honest framing in the brief: this grades the semantics, not enforcement — lesson 2 does enforcement. (2) `web`, THE ONE LESSON THAT NEEDS ENGINE WORK (see engineNeeds). Learner sets `window.POLICY` to a policy string; the harness builds a nested sandboxed iframe whose head carries it as a `<meta http-equiv>`, runs a fixed battery of five payloads inside, and postMessages back which ran. Test `await T.sleep(400)` then asserts `__CSP_RESULTS.inlineScript === false`, `__CSP_RESULTS.imgOnerror === false`, `__CSP_RESULTS.evalCall === false`, and `__CSP_RESULTS.ownStylesheet === true` — a policy of `default-src 'none'` blocks the payloads but also breaks the page, so it fails; the learner must write a policy that is both restrictive and functional. (3) `js`, works today. Learner writes `securityHeaders(res)` middleware (a `srv-u4` middleware, deliberately) adding `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Strict-Transport-Security`, and the CSP from lesson 1. Test asserts the exact header map on a real response and that existing headers survive. Second half: `isFramable(headers, parentOrigin)` — four asserted decisions across `DENY`, `SAMEORIGIN` and a `frame-ancestors` list. (4) PROJECT, `web`, 60xp/40min. ShoutBoard is a working comment board broken in five specific ways: `innerHTML` render, a `javascript:` avatar link, an API key in the source, a client-side `window.currentUser.isAdmin` flag gating the delete button, and no length cap. Five graded step-groups, one per hole: a stored payload renders as literal text with `window.__fired === undefined`; the `javascript:` avatar href is dropped while an `https:` one survives (`T.attr`); `findSecrets` over the page's script text returns `[]` and the feature still works against the mock; the test SETS `window.currentUser.isAdmin = true` from the grader and asserts `deletePost(2)` still fails and the post survives (because the decision moved to the mocked server), then asserts the admin-token path succeeds; and a 5000-char comment is refused with a visible message in `#error` while nothing is added to the store. If the CSP lab is deferred, this unit ships as four items and the course as 32.

## Risks
- The CSP nested-frame lab may not be buildable at all. Nested sandboxed srcdoc iframes inherit an opaque origin, and I have not verified that a <meta http-equiv="Content-Security-Policy"> is honored in that position in Chrome. Spike it BEFORE writing sec-u7-2. Mitigation is cheap and already designed in: cut the lesson, ship U7 at four items and the course at 32, and teach CSP through the parsePolicy interpreter with an honest brief saying the browser is what enforces it.
- Async sentinel flakiness. <img onerror> fires asynchronously; the grader starts 60ms after load. Every XSS assertion in U2, U3 and both projects must open with `await T.sleep(120)`. Miss one and it passes on the dev machine and fails on a slow one — the worst failure mode for a course whose whole premise is 'watch it fire.' Make it a rule in the unit's authoring notes, and have tools/validate.js flag any sec- step whose test references __fired without a preceding T.sleep.
- The learner writes working exploits. The payloads are alert-level OWASP textbook material and the targets are all inside his own sandbox, so the actual risk is near zero — but the framing matters. Each attack lesson's brief needs one line establishing that this is a lab, and the course blurb should say 'break your own app' rather than anything that reads as offensive-security marketing.
- Hand-rolled defenses mistaken for production-ready. A learner who writes escapeHtml and a 40-line sanitizer can conclude he doesn't need DOMPurify — which is worse than not taking the course. Mitigation: every such lesson's brief ends with the same explicit line, the U3 quiz has a question whose correct answer is 'use a maintained library,' and the toy SQL and toy hash are both labelled 'never ship this' in their own starter comments.
- Drift toward theory. A security course is unusually easy to fill with pure functions that are about security without ever being security — nine of the 33 items are exactly that shape. U2 and the two projects are what make it real. If schedule pressure hits, cut a U4 lesson or a U5 lesson; never cut a U2 lesson or a project.
- Scope creep into cybersecurity. TLS, certificates, ports, threat modeling, npm audit and dependency CVEs all feel adjacent and none of them are auto-gradeable in a browser. Supply-chain goes to the proposed Node/npm course, HTTPS/HSTS-in-practice to the proposed Deploy course. Everything that stays here has a test that asserts something.
- Course 7 is left with two dangling promises in srv-u5's quiz explanations (the 403 note and the bcrypt note) that now point at a course that may ship months later. Edit both explain strings when this course lands, or they read as a bug.
- Simulation honesty debt. Three lessons grade a stand-in rather than the real thing: the httpOnly cookie jar (sec-u5-3), the .gitignore classifier (sec-u5-2), and the reflected-XSS 'URL' that is really a const (sec-u2-1). Each is defensible and each is labelled in its brief — but if a fourth or fifth accumulates, the course starts teaching a fictional web. Treat three as the ceiling.
